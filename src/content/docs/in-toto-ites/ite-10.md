title: "ITE-10: supporting contextual attestations in layouts"
description: The draft proposal for verifying multiple contextual predicate types inside in-toto layouts and sublayouts.
---

## Summary

ITE-10 asks a natural follow-up question after [ITE-6](../ite-6/): if
attestations can now have many predicate types, how should in-toto layouts
verify them?

The draft updates the layout model so a step can expect one or more predicate
types instead of only classic links.

## The key idea

ITE-10 groups predicates into two broad classes:

- `transformational` predicates, such as classic links and provenance, where a
  step consumes materials and produces products.
- `informational` predicates, such as test results or code review evidence,
  where the step records claims about artifacts without necessarily producing a
  new artifact.

That split lets layouts keep artifact chaining semantics while also reasoning
about richer evidence.

## Example: step schema in the draft

```yaml
name: string
command: list of strings
expected_materials: list of artifact rules
expected_products: list of artifact rules
expected_predicates:
  - predicateType: string
    functionaries: list of authorized key IDs
    threshold: int
```

## Why it matters

This is the proposal that tries to reconnect the modern attestation framework
with the original in-toto layout verifier. Without something like ITE-10, the
ecosystem can generate rich attestations but still has to fall back to older
layout semantics when it wants step-by-step supply chain verification.

## Example: what the verifier is trying to reason about

```text
source checkout  --produces--> source tree
       |
       +--> code review predicate about that source tree
       |
       +--> build provenance predicate about the binary produced later
```

ITE-10 is the proposal that says a layout should be able to talk about both
arrows in one verification model.

## Implementation status in this workspace

I did not find `expectedPredicates` or an equivalent classic in-toto layout
feature in the current `witness`, `go-witness`, `rookery`, or `aflock` repos.
The current workspace does support:

- multiple predicate types in the attestation framework,
- attestation collections,
- and policy-style verification over those collections.

But that is not the same as implementing ITE-10's layout schema and verifier
workflow as written.

## Why it is still relevant

ITE-10 is useful for understanding the architectural gap between:

- modern attestations generated by `witness`, `go-witness`, and `aflock`,
- and the future state where a layout verifier could natively chain them.
